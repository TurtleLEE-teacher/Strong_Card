# Strong Card — 카드 혜택 실적 트래커 개발 계획

> 노션에 자동 적재되는 카드 결제 내역을 읽어, **카드별 전월실적 진행률**과 **혜택 한도 소진 현황**을
> Bar 형태로 보여주고, 실적/혜택 관련 알림을 보내는 개인용 PWA.
> (레퍼런스: 예전 "더쎈카드" 앱)

---

## 1. 확정된 기술 결정

| 항목 | 결정 | 비고 |
|---|---|---|
| 앱 형태 | **PWA 단일 코드베이스** | 웹 + 홈화면 설치형 앱을 하나로. 앱스토어 심사 불필요 |
| 데이터 저장 | **Notion 직접 조회** | 별도 DB 없음. Notion이 유일한 source of truth |
| 카드 식별 | **Notion 속성 추가 + 앱 파싱 병행** | 원문에서 뒷4자리 파싱 → Notion에 역기입 |

### 파생 결정 (별도 DB를 안 쓰는 데서 따라오는 것)

별도 DB가 없으므로 **알림 중복 발송 방지 상태도 Notion에 저장**해야 한다.
→ 거래 행에 `알림 상태` 속성을 두고, 월 단위 알림은 별도 소형 DB(`🔔 Alert_Log`)로 관리한다.

## 2. 현재 Notion DB 진단

**대상**: `💳 Card_Transactions` (`collection://9dff87c6-4dbd-4791-be01-e7f4851e19fa`)
**현재 적재량**: 2건 (2026-07-02, 2026-07-30) — 자동화 초기 단계

### 기존 속성

| 속성 | 타입 | 트래커에서의 역할 |
|---|---|---|
| `사용 내역` | title | 가맹점명 (혜택 매칭 1차 키) |
| `가맹점` | text | 가맹점 원문 (혜택 매칭 2차 키) |
| `금액` | number | ⚠️ 해외결제는 **외화 원금** |
| `통화` | select | KRW/USD/JPY/EUR/기타 |
| `사용 일시` | date | 승인일시(KST) — **실적 기간 산정 기준** |
| `카드명` | select | ⚠️ **카드사 단위** (신한/삼성/현대/국민…) |
| `카드 종류` | select | 신용/체크/법인/선불 |
| `결제 구분` | select | 일시불/할부/해외/취소·환불 |
| `카테고리` | select | 식비/카페/교통/… (혜택 매칭 보조 신호) |
| `취소 여부` | checkbox | 실적 제외 판정 |
| `승인번호` | text | ⚠️ 실제 승인번호 아님. 합성키 (`KB-6089-N-07301032-2500`) |
| `원문` | text | ⭐ **뒷4자리 · 누적실적 · 통화 추출 원천** |
| `할부 개월` | number | 할부 실적 인정 방식 판정 |
| `기준월` | formula | `2026-07` 형태 |

### 발견된 문제 3가지

#### 🔴 P1. 카드 6장을 구분할 수 없음 (최대 블로커)

`카드명`이 카드사 단위라 국민 2장(탄탄대로 / 쿠팡와우), 신한 2장(Discount Plan / EV)이 섞인다.
카드별 실적·한도가 완전히 다르므로 **구분 없이는 앱 자체가 성립하지 않는다.**

**해결**: 원문에 뒷4자리가 존재함을 확인.

```
<제목: KB국민카드6089 승인>          → 6089
삼성2055해외승인 이*석                → 2055
승인번호: KB-6089-N-07301032-2500    → 6089 (백업 소스)
```

→ 뒷4자리 → 카드 상품 매핑 테이블이 전체 설계의 축.

#### 🔴 P2. 해외결제 금액이 원화가 아님

```json
{ "가맹점": "ANTHROPIC,PBC", "금액": 22, "통화": "USD", "결제 구분": "해외" }
```

`금액`을 그대로 합산하면 22원으로 잡힌다. **원화 환산 컬럼이 필수.**

#### 🟢 P3. (기회) 카드사 공식 실적 누계가 원문에 들어있음

```
승인시각 07/30 10:32
누적 2,040,509원          ← 카드사가 계산한 공식 누계
```

이건 **정답지**다. 우리 계산값과 대조하면 "제외 항목 규칙이 맞는지" 자가검증이 된다.
파싱해서 저장하고, 대시보드에 `우리 계산 / 카드사 누계` 오차를 노출한다.

## 3. Notion 스키마 보강안

### 3-1. `💳 Card_Transactions`에 추가할 속성 (6개)

| 속성명 | 타입 | 채우는 주체 | 용도 |
|---|---|---|---|
| `카드 뒷4자리` | text | 앱 (원문 파싱) | 카드 상품 식별 키 |
| `카드 상품` | select | 앱 (매핑 결과) | 탄탄대로 / 쿠팡와우 / Amex Blue / ZERO Ed2 / Discount Plan / 신한EV |
| `원화금액` | number | 앱 (환산) | 실적·혜택 계산의 **유일한 금액 기준** |
| `실적 인정` | select | 앱 (룰 엔진) | 인정 / 제외-취소 / 제외-공과금 / 제외-상품권 / 제외-무승인 / 제외-기타 |
| `혜택 적용액` | number | 앱 (룰 엔진) | 이 거래로 받은 할인·적립 금액 |
| `알림 상태` | select | 앱 (알림 발송기) | 대기 / 발송완료 / 대상아님 |

> `실적 인정`을 checkbox가 아닌 select로 두는 이유: 제외된 이유를 노션에서 바로 보고 룰 오류를 잡기 위함.

### 3-2. 신규 소형 DB `🔔 Alert_Log`

월 단위 알림(실적 미달 경고, 구간 달성 등)의 중복 발송 방지용.

| 속성명 | 타입 | 용도 |
|---|---|---|
| `알림 키` | title | `2026-07:탄탄대로:tier_warning_d7` (멱등 키) |
| `카드 상품` | select | 대상 카드 |
| `기준월` | text | `2026-07` |
| `알림 유형` | select | 혜택적용 / 실적미달 / 실적달성 / 한도소진임박 |
| `발송 일시` | date | 발송 시각 |
| `본문` | text | 실제 발송된 메시지 |

### 3-3. 카드 마스터 · 혜택 룰은 **레포 코드**로 관리

Notion이 아니라 `config/cards/*.ts`에 둔다.

- 이유: 혜택 조건이 복잡(구간별 한도, 건당 최소금액, 프로모션 종료일)해서 Notion 속성으로는 표현이 안 된다
- 타입 안정성 + Git 버전 관리 + 테스트 가능
- 프로모션 종료(예: 쿠팡와우 4% → 2%)를 `effectiveFrom` / `effectiveUntil`로 날짜 버전 관리

### UI에 미치는 영향

**무실적 카드 2장(쿠팡와우, ZERO)은 실적 바가 무의미하다.**
→ 카드 위젯을 2가지 타입으로 나눈다.

- **실적형 카드**: 실적 바 + 혜택 한도 바 (2단)
- **무실적 카드**: 혜택 한도 바만 (1단, 또는 ZERO처럼 무제한이면 "이번 달 적립액" 숫자만)

## 5. 도메인 모델

### 5-1. 카드 마스터 (`config/cards/*.ts`)

```ts
interface Card {
  id: string;                    // 'kb-tantandaero'
  issuer: '국민' | '신한' | '삼성' | '현대';
  name: string;                  // 'KB국민 탄탄대로 Miz&Mr 티타늄'
  last4: string[];               // ['6089']  — 재발급 대비 배열
  active: boolean;               // 안 쓰는 카드 숨김
  annualFee: number;

  performance: {
    required: boolean;           // 무실적 카드면 false
    window: 'prev-month';        // 전월 1일~말일, 승인일 기준
    tiers: SpendTier[];          // [] 이면 실적 무관
    exclusions: ExclusionRule[]; // 카드사별 실적 제외 항목
    countsForeignSpend: boolean; // 해외결제 실적 인정 여부
    installmentPolicy: 'full' | 'monthly'; // 할부 인정 방식
  };

  benefits: BenefitRule[];
  monthlyBenefitCap?: TierCap[]; // 카드 통합 한도 (구간별로 다름)
}

interface SpendTier {
  threshold: number;             // 400_000
  label: string;                 // '40만원 구간'
  totalBenefitCap: number;       // 이 구간의 월 통합 할인한도
}
```

### 5-2. 혜택 룰

```ts
interface BenefitRule {
  id: string;
  label: string;                 // '스타벅스 20% 할인'
  type: 'discount' | 'point';    // 할인 vs 적립
  match: MerchantMatcher;        // 브랜드/카테고리/MCC 매칭
  rate: number;                  // 0.20
  minAmountPerTx?: number;       // 건당 최소 결제금액
  capPerTx?: number;             // 건당 한도
  capPerMonth?: number | TierCap[]; // 월 한도 (구간별 가능)
  effectiveFrom?: string;        // '2026-01-01'
  effectiveUntil?: string;       // '2026-10-15'  ← 쿠팡와우 프로모션
}
```

### 5-3. 계산 결과

```ts
interface CardMonthlySnapshot {
  cardId: string;
  month: string;                 // '2026-07'

  // 이번 달 실적 (→ 다음 달 혜택을 결정)
  currentSpend: number;
  excludedSpend: number;
  currentTier: SpendTier | null;
  nextTier: SpendTier | null;
  remainingToNextTier: number;
  issuerReportedSpend?: number;  // 원문 '누적 N원' 파싱값
  reconciliationDelta?: number;  // 우리 계산 - 카드사 누계

  // 이번 달 적용 중인 혜택 (← 지난달 실적으로 확정)
  appliedTier: SpendTier | null;
  benefitUsage: BenefitUsage[];  // 혜택별 소진액 / 한도
  totalBenefitUsed: number;
  totalBenefitCap: number;
}
```

> ⚠️ **핵심 개념**: 실적과 혜택은 **한 달 어긋나 있다.**
> - 이번 달 실적 → **다음 달** 혜택 구간을 결정
> - 이번 달 혜택 한도 ← **지난달** 실적으로 이미 확정
>
> 대시보드에서 이 둘을 섞으면 사용자가 반드시 혼란스러워한다. 명시적으로 분리 표기한다.

## 6. 실적 계산 규칙

### 산정 기간
전월 1일 00:00 ~ 말일 23:59:59 (KST), **승인일(`사용 일시`) 기준**

### 공통 제외 항목
- 취소·환불 (`취소 여부` = true 또는 `결제 구분` = 취소·환불)
- 각종 세금 및 공과금, 아파트 관리비
- 상품권 / 선불카드 구입·충전
- 무승인 전표 (교통요금, 자판기, 터널통행료, 항공기 기내)
- 대학(대학원) 등록금, 정부지원금
- 각종 수수료·이자·연체료·연회비
- 단기카드대출(현금서비스), 장기카드대출(카드론)

카드사별 세부 차이는 `Card.performance.exclusions`로 개별 정의한다.

### 가맹점 → 혜택 매칭 파이프라인

```
가맹점 원문
  → 정규화 (특수문자·지점명·사업자형태 제거)
     예: '(주)아방가르드(아방' → '아방가르드'
         '스타벅스*강남점'      → '스타벅스'
  → 브랜드 사전 매칭 (config/merchants.ts)
  → 혜택 카테고리 결정
  → [실패 시] Notion `카테고리` 속성으로 폴백
  → [그래도 실패 시] '미분류' 처리 + 대시보드에 노출
```

**미분류 가맹점 관리 화면**을 반드시 만든다. 초기엔 매칭 실패가 대량 발생하며,
이걸 사용자가 웹에서 매핑 추가하지 못하면 앱이 금방 신뢰를 잃는다.

- 혜택별 소진 바 (전체)

## 8. 알림 설계

| # | 유형 | 트리거 | 예시 문구 |
|---|---|---|---|
| 1 | **혜택 적용** | 신규 거래 sync 시 혜택 매칭됨 | "스타벅스 20% 할인 1,000원 적용 (Amex Blue)" |
| 2 | **실적 미달 경고** | 매월 D-7 / D-3 / D-1 | "탄탄대로 80만 구간까지 12만원 남음" |
| 3 | **실적 구간 달성** | 실적이 임계값 돌파 | "Discount Plan 80만 구간 달성! 다음 달 한도 7만원" |
| 4 | **한도 소진 임박** | 혜택 한도 80% 소진 | "스벅 할인 4,500/5,000원 — 이 카드 그만 쓰세요" |

**중복 방지**: 1번은 거래 행 `알림 상태`, 2~4번은 `🔔 Alert_Log`의 멱등 키로 차단.

**전송 경로**: Web Push (VAPID) → Service Worker
> ⚠️ iOS 제약: 반드시 **홈 화면에 추가**해야 푸시가 동작한다. 온보딩에서 안내 필요.

## 9. 기술 스택

| 레이어 | 선택 | 근거 |
|---|---|---|
| 프레임워크 | Next.js 15 (App Router) + TypeScript | 웹/PWA 단일 코드베이스, 서버에서 Notion 토큰 보호 |
| 스타일 | Tailwind CSS v4 + shadcn/ui | 빠른 구축, 다크모드 |
| 차트 | **순수 CSS/SVG 바** (라이브러리 없음) | 필요한 게 진행률 바뿐. 라이브러리는 과함 |
| Notion | `@notionhq/client` | 공식 SDK |
| 캐싱 | Next.js `revalidate` + 서버 메모리 캐시 (5분) | Notion API 3req/s 제한 회피 |
| 푸시 | `web-push` (VAPID) + 커스텀 Service Worker | 무료, 서버 불필요 |
| 배포 | Vercel | 무료 티어 |
| 스케줄러 | **GitHub Actions cron** → 앱의 `/api/cron/*` 호출 | ⚠️ Vercel Hobby cron은 하루 1회 제한. GitHub Actions는 분 단위 무료 |
| 인증 | 단일 사용자 비밀번호 (미들웨어) | 금융 데이터. 공개 URL 방치 불가 |
| 테스트 | Vitest | **룰 엔진은 테스트 필수** |

### 환경 변수

```
NOTION_API_KEY          Notion 통합 토큰
NOTION_TX_DB_ID         Card_Transactions DB ID
NOTION_ALERT_DB_ID      Alert_Log DB ID
VAPID_PUBLIC_KEY        Web Push
VAPID_PRIVATE_KEY       Web Push
CRON_SECRET             GitHub Actions → API 인증
APP_PASSWORD            앱 접근 비밀번호
EXCHANGE_RATE_API_KEY   환율 (또는 무료 API)
```

## 11. 사용자 확인이 필요한 사항

### 🔑 필수 (Phase 0 진입 전)

1. **카드 6장의 뒷 4자리**
   - 확인된 값: `6089` (국민 — 탄탄대로? 쿠팡와우?), `2055` (삼성 — Amex Blue로 추정)
   - 나머지: 현대 ZERO, 신한 Discount Plan, 신한 EV, 국민 나머지 1장
   - ※ 카드번호 전체가 아니라 **뒷 4자리만** 필요

2. **Notion 통합(Integration) 토큰** — 앱이 DB를 읽고 쓰려면 필요

### 🔧 권장 (있으면 정확도 상승)

3. 각 카드의 **현재 적용 중인 실적 구간** (초기 검증용)
4. 실제로 안 쓰는 카드가 있는지 (`active: false` 처리)
5. 신한 Discount Plan은 **선택형 할인 영역**이 있을 수 있음 — 어떤 영역을 골랐는지
